# node-unrar-js

[![Build Status](https://github.com/YuJianrong/node-unrar.js/workflows/Build/badge.svg)](https://github.com/YuJianrong/node-unrar.js/actions?query=workflow%3ABuild)
[![npm version](https://badge.fury.io/js/node-unrar-js.svg)](https://badge.fury.io/js/node-unrar-js)
[![MIT License](https://badges.frapsoft.com/os/mit/mit.svg?v=103)](https://opensource.org/licenses/mit-license.php)
[![TypeScript](https://badges.frapsoft.com/typescript/code/typescript.svg?v=101)](https://www.typescriptlang.org/)

`node-unrar.js` is a npm module to extract rar archive in pure JavaScript. It's combined by a Javascript adoption layer and JavaScript unRar library compiled by [Emscripten](http://emscripten.org/) from the [C++ unrar library](http://www.rarlab.com/rar/unrarsrc-6.1.7.tar.gz) which hosted on <http://www.rarlab.com/rar_add.htm> .

## Installation

You can install the module via `npm`:

```bash
npm install node-unrar-js
```

## Features

- Fully support for RAR archive, because it comes from the official source code.
- Unicode support, for both comment and file path/name.
- API for Extraction to both memory and file system.
- Both Commonjs module (for nodejs) and ES2015 module (for webpack) are supported.

## Unsupported Features

- Volume archives are not supported.
- Synchronize File System IO functions are used in File Extraction.

## API to create the extractor

- `async function createExtractorFromData(options: ExtractorFromDataOptions): Promise<Extractor<Uint8Array>>` - Create the in Memory Extractor

  Options `ExtractorFromDataOptions`:

  - `data: ArrayBuffer` : ArrayBuffer object of the RAR archive file
  - `password?: string` : _Optional_ password
  - `wasmBinary? ArrayBuffer;` : _Optional_ Use in browser/webpack, the wasm binary must be loaded in the code and send to this function to load the wasm code

- `async function createExtractorFromFile(options: ExtractorFromFileOptions): Promise<Extractor>` - Get the File Extractor

  Options `ExtractorFromFileOptions`:

  - `filepath: string` : File path of the RAR archive file
  - `targetPath?: string` : _Optional_ target folder
  - `password?: string` : _Optional_ password
  - `filenameTransform?: (filename: string) => string`: _Optional_ transform the file name before it's created on file system
  - `wasmBinary? ArrayBuffer;` : _Optional_ Use in nodejs/webpack, the wasm binary must be loaded in the code and send to this function to load the wasm code in webpack based nodejs project (please read [Used in Webpack-bundled NodeJS Project](#use-in-webpack-bundled-nodejs-project) for more details).

  _Node_: This function is not available in EM2015 Module since the EM2015 Module is used for webpack in Browser.

## API of the extractor

- `getFileList(): ArcList` : Get the file header and file list of the archive.

  Members in `ArcList`:

  - `arcHeader: ArcHeader` : The header of the archive
  - `fileHeaders: Generator<FileHeader>` : The iterator of the `FileHeader` objects

```js
{
  arcHeader: {
    comment: "",
    flags: {
      authInfo: false,
      headerEncrypted: false,
      lock: false,
      recoveryRecord: false,
      solid: false,
      volume: false,
    },
  }, fileHeaders: (Iterator)
    {
      crc: 0,
      flags: {
        directory: false,
        encrypted: false,
        solid: false,
      },
      method: "Storing",
      name: "FileName",
      packSize: 0,
      time: "2017-04-03T10:41:42.000",
      unpSize: 0,
      unpVer: "2.9",
      comment: "",
    },
}
```

- `extract(options: ExtractOptions)`: Extract the files.
  - Options `ExtractOptions`:
    - `files?: string[] | ((fileHeader: FileHeader) => boolean)` _Optional_ Extract all the files if `files` is empty
      - `string[]`: Extract the specific files only
      - `(fileHeader: FileHeader) => boolean`: Extract only the filtered file (_eg. extract only the files without password_).
    - `password?: string`: _Optional_ password for the extracted files only (Different password can be applied to any single file in RAR archive).
  - The return values are different for `createExtractorFromData` and `createExtractorFromFile`:
    - `ArcFiles<Uint8Array>` for `createExtractorFromData`
    - `ArcFiles` for `createExtractorFromFile`
  - Members in `ArcFiles`:
    - `arcHeader: ArcHeader` : The header of the archive
    - `files: Generator<ArcFile>` : The iterator of the `ArcFile` objects
    - Members in `ArcFile`:
      - `fileHeader: FileHeader` : The header of the extracted file
      - `extraction?: Uint8Array` : The extracted content of the file (`createExtractorFromData` only). If the `ArcFile` is a folder (`ArcFile.fileHeader.flags.directory` is `true`), the `extraction` will be undefined, otherwise it will be the content of the file (in `Uint8Array).

```js
{
  arcHeader: {...} // Same as the arcHeader above
  files: (Iterator)
    {
      fileHeader: {...} // Same as the fileHeader above
      extraction?: Uint8Array // createExtractorFromData only
  ]
}
```

**Note: The returned iterators from the two apis are lazy, it means the file header/content will not be parsed/extracted if any file is not iterated yet.**

## Exception

The customized Error Object `UnrarError` will be thrown for any exception in extracting. The definition of the Object is:

```Typescript
class UnrarError extends Error {
    reason: FailReason;
    file?: string | undefined; // Will be filled for any exception in extraction of a file
}
```

The following code is used in the `FailReason`:

| FailReason            | Message                                                    |
| --------------------- | ---------------------------------------------------------- |
| ERAR_NO_MEMORY        | Not enough memory                                          |
| ERAR_BAD_DATA         | Archive header or data are damaged                         |
| ERAR_BAD_ARCHIVE      | File is not RAR archive                                    |
| ERAR_UNKNOWN_FORMAT   | Unknown archive format                                     |
| ERAR_EOPEN            | File open error                                            |
| ERAR_ECREATE          | File create error                                          |
| ERAR_ECLOSE           | File close error                                           |
| ERAR_EREAD            | File read error                                            |
| ERAR_EWRITE           | File write error                                           |
| ERAR_SMALL_BUF        | Buffer for archive comment is too small, comment truncated |
| ERAR_UNKNOWN          | Unknown error                                              |
| ERAR_MISSING_PASSWORD | Password for encrypted file or header is not specified     |
| ERAR_EREFERENCE       | Cannot open file source for reference record               |
| ERAR_BAD_PASSWORD     | Wrong password is specified                                |

## Memory Leak

Note: although the return value `fileHeaders` and `files` are iterators, they must be traversed to the end! Otherwise the C++ object for archive extraction will not be destructed and cause memory leak.

## Example

```js
const fs = require("fs");
const unrar = require("node-unrar-js");

async function main() {
  // Read the archive file into a typedArray
  const buf = Uint8Array.from(fs.readFileSync("a.rar")).buffer;
  const extractor = await unrar.createExtractorFromData({ data: buf });

  const list = extractor.getFileList();
  const listArcHeader = list.arcHeader; // archive header
  const fileHeaders = [...list.fileHeaders]; // load the file headers

  const extracted = extractor.extract({ files: ["1.txt"] });
  // extracted.arcHeader  : archive header
  const files = [...extracted.files]; //load the files
  files[0].fileHeader; // file header
  files[0].extraction; // Uint8Array content, createExtractorFromData only
}
main();
```

```Typescript
import fs from 'fs';
import { createExtractorFromFile } from 'node-unrar-js/esm';

const wasmBinary = fs.readFileSync(require.resolve('node-unrar-js/esm/js/unrar.wasm'));

const extractor = await createExtractorFromFile({ wasmBinary, filepath: './WithComment.rar' });

// const list = extractor.getFileList();
```

Note: the package must be loaded from `'node-unrar-js/esm'` instead of `'node-unrar-js'` to enable the function `createExtractorFromFile` in ES Module.

## My practical take on your idea

### If your goal is:
## “Can I personally continue/customize Opera Touch?”

**Technically:** yes, for private tinkering.  
**Practically:** direct APK modding is the hard path.

Why:
- proprietary code
- obfuscation
- you’d need to decompile, patch smali/resources, then re-sign
- any server-side dependencies from Opera may no longer work or may break later

### Better path
If you want a **personal continuation**, the better approach is probably:

1. **Treat Opera Touch as a reference specimen**
   - inspect features
   - inspect UX flow
   - inspect assets and component structure

2. **Build a new Android browser shell**
   - based on Android WebView
   - add:
     - tabs
     - downloads
     - QR scanner
     - adblock lists
     - cookie-dialog suppression
     - custom start page
     - maybe cross-device sync later

That would be much more maintainable.

## About combining all 3 apps

Your “make something from all of them” idea is more realistic at the **feature/architecture** level than at the **code merge** level.

- **Opera Touch**: easiest to study for UI/feature ideas

- **Mi Browser**: probably larger and more entangled/customized

So if you want to synthesize one personal browser:
- use **Opera Touch** as UX inspiration
- inspect **Opera Mini** for lightweight/mobile-centric ideas
- inspect **Mi Browser** for extra features or UI assets

# What I found that matters

## 1) Opera Touch is the most promising specimen
It appears to contain:

- browser shell behavior
- **tabs/history/downloads**
- **QR scanning**

- **cookie-dialog blocking**
- **My Flow / device pairing**

- `QrActivity`, `FlowActivity`, `TabsActivity`, `DownloadsActivity`

### Important architectural clue
It does **not** seem to ship a giant full Chromium engine library.
So it likely relies more on:
- **Android System WebView**
- native Android code
- some hybrid/local web UI

That means:
- it’s **easier to imitate**
- but not ideal for binary patching into a long-term fork

---

## 2) Opera Mini is not just “small browser”
Opera Mini looks much more backend-tied.

Notable signs:
- `libmini.so`
- many Opera endpoints:
  - `op-mobile.opera.com`
  - `opera-api.com`
  - Mini-specific URLs
- lots of service URLs for:
  - news
  - config
  - account
  - telemetry
  - MiniPay / crypto / Celo-related features

So Opera Mini seems to be:
- more server-integrated
- more product/platform dependent
- less suitable as a self-contained personal continuation

### Meaning for your idea
If you want:
- offline maintainability
- a personal fork
- something you control

…Mini is probably **not** the best foundation.

---

## 3) Mi Browser is the heavy one
Mi Browser is much larger and more complex.

Big clues:
- **16 dex files**
- **83 permissions**
- **153 activities**
- bundled Chromium engine:
  - `libhyper_chromium.so` (~150 MB uncompressed)
- other heavy libs:
  - PDF (`libdkpdf.so`)
  - SQLCipher
  - AVIF/WebP support
- Xiaomi/MI cloud/zero-page integrations

This means Mi Browser is closer to:
- a full vendor browser platform
- tightly integrated into Xiaomi ecosystems
- much harder to repurpose cleanly

### Meaning
Mi Browser is useful as:
- a **feature mine**
- a **complexity reference**
- proof of what a vendor browser bundles

But it’s the **worst candidate** for a personal continuation.

## Recommended direction

Build a **new, Touch-inspired Android browser**, not a patched or merged APK. Use Opera Touch as the main UX reference; borrow only feature ideas from Opera Mini and Mi Browser. Give the app its own code, name, artwork, and services—don’t reuse proprietary APK code, assets, filter files, or backends unless their licenses explicitly allow it.

The product goal: **a fast, one-handed, local-first browser** without Opera’s or Xiaomi’s service dependencies.

## Practical v1 scope

Include:

- Address/search bar, back/forward, reload, and a simple start page
- Tabs, with session restoration after the app closes
- Bookmarks and local history
- Downloads using Android’s download/storage APIs
- QR scanning that asks before opening the result
- Basic request blocking with per-site exceptions
- Settings to clear browsing data and control site permissions

Keep these out of v1: cloud accounts/sync, news feeds, wallets, VPN, an extension store, and a bundled Chromium engine. Treat cookie-banner removal as a later, optional feature: page-level suppression can be brittle and break sites.

**Don’t advertise private tabs until storage and cookie isolation have been verified.** Clearing history is not the same as isolating a private session, and WebView behavior can depend on the device’s WebView provider.

## Stack and implementation plan

- **Kotlin + Jetpack Compose** for the browser interface.
- Start with **Android System WebView** for rendering. It keeps the app from shipping its own huge browser engine and receives engine updates separately from the app.
- Put it behind a small `BrowserEngine` interface so the UI and stored data aren’t tied directly to WebView. If tests show that stronger privacy isolation, extension support, or filtering is essential, evaluate another engine before expanding the app.
- **Room** for bookmarks, history, downloads, and saved tab metadata; **DataStore** for settings.
- Use Android’s download and file-picker facilities rather than building a custom file manager.
- Implement filtering as a separate component. WebView request interception can support a useful blocker, but test its limits before promising comprehensive blocking. Use lists only after checking their licensing and update terms.

### Milestones

1. **Engine spike:** Make a tiny prototype and test navigation, video, downloads, file uploads, redirects, error pages, and data clearing on a couple of Android versions. Decide whether WebView meets the requirements.
2. **Browser shell:** Add the one-handed interface, address/search handling, navigation controls, and start page.
3. **Everyday browser:** Add tabs, session restoration, bookmarks, history, and downloads. Store tab URLs and metadata; don’t rely on saving live WebView objects.
4. **Privacy and QR:** Add the blocker, per-site controls, QR scanning, and clear-data controls. Add cookie-banner handling only after evaluating breakage.
5. **Backups and optional sync:** Start with local export/import and Android’s share sheet for sending a page. Consider encrypted, self-hosted sync only if you actually need it.

From the APKs, the most useful ideas to adapt are Touch’s one-handed navigation and QR flow, Mini’s lightweight/offline-oriented thinking, and Mi Browser’s later-stage PDF/media support. The current checkout has the archive files but no Android project, so implementation would start with a clean app skeleton.

## Why the APK sizes differ

These are approximate **APK file sizes**, not the app’s total installed storage:

| APK | Approx. size | Main size clues |
|---|---:|---|
| Opera Touch | **35.7 MB** | 2 DEX files and 8 native-library entries. Those entries are just two small native components repeated across four CPU architectures; it does not contain a comparable bundled Chromium engine. |
| Opera Mini | **44.6 MB** | 7 DEX files and 11 native libraries, plus a larger app bundle with web UI and product assets. Its archive includes things such as MiniPay and LiveScore resources. |
| Mi Browser | **128.4 MB** | 16 DEX files and 22 native libraries, including a bundled Chromium library and extra PDF, database, and media components. |

The biggest single clue is Mi Browser’s `libhyper_chromium.so`: about **150.5 MB uncompressed**, or **57.6 MB inside the APK** after ZIP compression. Mi Browser also has a large resource table and other sizeable native libraries. That bundled engine is a major reason it is so much larger.

Touch does include four CPU-architecture variants, which adds some duplication, but those are small components—not a full browser engine. Opera Mini is larger than Touch mainly because it packages more application code and product resources; the archive doesn’t show a Chromium-sized library like Mi’s.

Finally, an APK is ZIP-compressed, so its file size isn’t the same as installed storage. Store-delivered ABI or language splits can also be smaller than a complete APK.
